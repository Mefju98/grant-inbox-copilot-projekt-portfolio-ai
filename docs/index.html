How it works

A fixed, inspectable pipeline

Each stage has a narrow responsibility. Retrieval limits the evidence set, Python owns the policy outcome, and uncertainty routes the case to a person.

One request, one bounded sequence. No autonomous tool selection.Model label is checked against fictional program rules.
Engineering choices

Built to be explainable

01

Evidence before generation

The API searches the fictional knowledge base first. With no relevant match, it skips the LLM and returns a review outcome.

02

Rules own the label

The model proposes facts and a draft. Deterministic Python checks the required criteria and prevents an unsupported recommendation.

03

Citations are grounded

Returned citation IDs are selected from retrieved documents according to the outcome and the policy criteria involved.

04

Bounded provider retries

Only transient provider and transport failures are retried, with a small hard limit and content-free attempt diagnostics.

05

Human escalation

Missing evidence, ambiguity, or conflicting definitive assessments suppress the recommendation and request review.

06

Privacy-minimized audit

The API audit records decision metadata, not inquiry text or extracted tax identifiers. The separate local demo queue is clearly marked as synthetic-only.

Safety and scope

Clear limits are part of the design

✓

Fictional data only

Every program rule and benchmark inquiry is synthetic. The project is not a real grant service.

✓

Not a funding decision

An `eligible` result is a preliminary screening outcome. A human must make any real decision.

✓

Lexical retrieval baseline

BM25 can miss paraphrases. Citation ID validation does not prove every sentence is entailed.

✓

Local queue, demo controls

The SQLite review queue has no authentication or retention automation. Do not put real applicant data in it.
